# benchbook 🦀

**Benchmark and profile documentation with deliberate milestones.**

`benchbook` records `go test -bench` results and pprof profiles, keeps an immutable history of *milestones*, compares
runs with statistics instead of vibes, and generates a static documentation site you can publish on GitHub Pages — with
one binary and one
`benchbook.toml`, reusable across every Go repository you own.

```console
$ benchbook status
📚 current run  (main @ 4f2a9c1, dirty)
📍 last milestone  m003  (2026-04-02, 8c1de07)

   geomean vs m003:  ns/op −12.4%   bytes/op −31.0%   allocs/op −33.3%   (9 benchmarks)
   🐢 ParseJSON/stream   8.4 µs → 9.1 µs   (+8.3%, p=0.004)
   ⚡ Concat             96 B → 32 B       (−66.7%, p=0.001)
```

## Install

```console
go install github.com/seyallius/benchbook/cmd/benchbook@latest
```

Requires **Go 1.27.0** or newer (`go.mod` pins `go 1.27.0`). The binary is self-contained: the site shell, its CSS and
the vendored `marked` + `highlight.js`
bundles are embedded with `go:embed`, so `benchbook` never needs network access at run time. (Change the module path in
`go.mod` if you fork it; nothing else refers to it.)

Dependencies are deliberately few and all of them boring: `spf13/cobra` for the command line (with `spf13/pflag`, which
it builds on), and `BurntSushi/toml` for the configuration file. Everything else — the statistics, the Markdown and SVG
rendering, the JSON encoder, the HTTP server for `serve` — is the standard library.

## Quickstart

```console
$ cd ~/code/myproject
$ benchbook init --name myproject      # writes benchbook.toml + .gitignore entries
$ benchbook run                        # 6 samples per benchmark → benchbook/current.json
$ benchbook profile                    # cpu + heap tables, attached to that run
$ benchbook milestone -m "baseline"    # m001, immutable, points at a commit
$ # ... write some code ...
$ benchbook run && benchbook status    # what changed, and whether it is real
$ benchbook profile                    # profile the run you are about to promote
$ benchbook milestone -m "sync.Pool for Concat"
$ benchbook build && benchbook serve   # read the whole story at http://localhost:8000
```

Then commit `benchbook/` and `docs/` (skip `benchbook/raw/`, which `init` adds to
`.gitignore`) and turn on GitHub Pages for the `docs/` folder. That is the whole loop.

## The model: runs, milestones and the source of truth

Two nouns, and the whole tool is built around not confusing them.

|            | **Run**                                  | **Milestone**                              |
|------------|------------------------------------------|--------------------------------------------|
| what it is | the working tree of measurements         | a frozen, named point in the history       |
| where      | `benchbook/current.json`                 | `benchbook/history/m004-pool-buffers.json` |
| lifetime   | overwritten by the next `benchbook run`  | kept forever, never rewritten              |
| created by | `benchbook run` (also `run --from-file`) | `benchbook milestone -m "label"` only      |
| intent     | "I measured something"                   | "I claim this is what the code does now"   |

Three rules follow from that, and they are the ones worth remembering:

1. **Intent is always explicit.** Nothing is ever promoted automatically. `run` never touches history; only `milestone`
   writes to it, and only when you say so.
2. **`benchbook` never claims to know why.** It cannot tell a rerun from an optimisation, and it does not pretend to: it
   reports that the numbers changed and how confident it is. You supply the meaning with the label and `--note`.
3. **Structured JSON is the source of truth.** `benchbook/current.json` and
   `benchbook/history/*.json` are the data. The Markdown pages, the SVG charts and the HTML site are *derived*: delete
   `docs/` and one `benchbook build` brings it back, byte-identical for identical inputs. Never edit a generated file —
   every one starts with `<!-- generated by benchbook: DO NOT EDIT -->` and the next build overwrites it.

`benchbook` writes only files it owns (`docs/` content pages it generates,
`benchbook/`, the shell assets). Your authored pages, your `README`, your `justfile`
are yours: the tool reads them at most and never rewrites them.

**Committable or not?** Commit `benchbook/current.json` *and* `benchbook/history/`:
the history is the point, and the current run is what the next comparison starts from.
`benchbook/raw/` holds untouched tool output and is regenerable; keep it out of git (`init` does that for you).

## Commands

```
benchbook <command> [flags]
```

| Command                                                                             | What it does                                                                        |
|-------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------|
| `init [--name PROJECT] [--force]`                                                   | write `benchbook.toml`, append the `.gitignore` entries, print a justfile snippet   |
| `run [--count N] [--filter RE] [--quick] [--from-file FILE] [--no-hw] [--no-build]` | run the benchmarks, record `current.json`, then rebuild the site                    |
| `profile [--bench NAME] [--pkg PACKAGE]`                                            | capture CPU + heap profiles and record their `pprof -top` tables on the current run |
| `status`                                                                            | compare the current run with the latest milestone (this is the everyday command)    |
| `milestone -m "label" [--note TEXT] [--allow-dirty] [--force]`                      | promote the current run into the immutable history                                  |
| `list [--limit N]`                                                                  | milestones, newest first, with their headline change                                |
| `compare A B [--metric NAME] [--force-incomparable]`                                | compare any two runs (`m003`, `current`, `latest`)                                  |
| `summary [--from ID] [--to ID] [--format md\|text\|json] [--findings N]`            | ready-to-paste PR/commit snippet                                                    |
| `build [--quiet]`                                                                   | regenerate every derived page and the site shell                                    |
| `serve [--port 8000] [--host 127.0.0.1]`                                            | serve the generated site locally                                                    |
| `version`, `help`, `--help`                                                         | the usual                                                                           |

Global flags: `--no-color` (also honours `NO_COLOR`), `-h`/`--help`.

Help is generated from the same command tree that parses the command line, so it can never drift out of date:
`benchbook --help` lists every command grouped by workflow,
`benchbook help <command>` and `benchbook <command> --help` are the same screen, and a typo gets a suggestion rather
than a shrug.

```console
$ benchbook --help
Measure:
  profile     Capture cpu and heap profiles and their pprof tables
  run         Run the benchmarks and record the working run

$ benchbook runn
❌ unknown command "runn" for "benchbook": did you mean "run"?
$ echo $?
2
```

**Exit codes** are part of the contract, so a script never has to parse English:

| Code | Meaning                                                                          |
|------|----------------------------------------------------------------------------------|
| `0`  | it worked                                                                        |
| `1`  | runtime failure: missing file, failing toolchain, unreadable config              |
| `2`  | usage error: bad flag, unknown command, missing `benchbook.toml`                 |
| `3`  | **refused** by a safety rule (dirty tree, too few samples) — no file was written |

### A note on `run --from-file`

CI machines, containers and laptops under thermal pressure all produce different numbers. When you want to record a
capture that was produced elsewhere, `run` will happily ingest it:

```console
$ go test -run '^$' -bench=. -benchmem -count=6 ./... | tee bench.txt   # on the bench box
$ benchbook run --from-file bench.txt
```

The raw text is kept exactly as it arrived under `benchbook/raw/`, and the provenance in `current.json` says it was
ingested — so a report can always be traced back.

### `--quick` and `--force`

`benchbook run --quick` records a single sample per benchmark. That is useful while iterating, but one sample is not a
measurement: the run is flagged
`indicative only`, `status` says so, and `milestone` refuses to promote it unless you pass `--force`. A forced milestone
is stamped with a ⚠ badge on the site and
`"forced": true` in the JSON, because a rule was overridden and the record should say so. Same story for a benchmark
with fewer samples than `stats.min_samples`.

## What "significant" means here

`benchbook` was written by someone who has been lied to by a single `-benchtime=1x`
run. Every percentage it prints is a claim, and claims have rules:

- **Medians with a spread, not means.** A benchmark sample set has no reason to be normal; the report shows the median
  (and ± half-range ÷ median as a crude spread)
  and keeps every raw sample in the JSON.
- **Two-sided Mann-Whitney U test, α = 0.05** (configurable) on the sample sets. It is rank-based, so one slow outlier
  cannot produce a fake 40% regression.
- **A minimum effect.** A change must be both significant *and* bigger than
  `stats.min_effect_pct` (1% by default) before it is labelled. Statistics and engineering significance are different
  questions.
- **A sample floor.** Fewer than `stats.min_samples` (6 by default) per side cannot be promoted, and fewer than 4 per
  side can never reach significance — those cells read
  `⚠ few samples` instead of inventing a percentage.
- **Comparability is checked, not assumed.** Each run carries a hardware fingerprint (GOOS, GOARCH, CPU model, core
  count) and the Go version. When they differ between two runs, percentages are suppressed and the reason is printed;
  the raw numbers stay visible and `--force-incomparable` is offered as an explicit, clearly-labelled override.
- **No per-sample best-of.** Cherry-picking the fastest of ten runs is how you get a beautiful result and a wrong one.

The same procedure is implemented twice on purpose: once in Go for the CLI and the generated pages, and once in
`internal/site/shell/compare.js` for the in-browser comparer. Both are checked against the same golden vectors
(`testdata/utest_vectors.json`,
`scripts/test-compare.mjs`), so the page and the terminal cannot disagree.

## Configuration reference

Everything lives in one `benchbook.toml` at the repository root. Every section is optional except `[project].name`;
unknown keys are rejected with the spelling and the offending name, because a silently ignored typo is worse than a
startup error.

```toml
[project]
name = "myproject"                     # required
emoji = "🦀"                            # header + favicon badge
repo_url = "https://github.com/me/myproject"

[paths]
data_dir = "benchbook"                     # current.json + history/ (commit this)
site_dir = "docs"                          # generated site (publish this)
raw_dir = "benchbook/raw"                 # raw output (gitignore this)

[bench]
packages = ["./..."]               # what `go test` is pointed at
args = ["-benchmem"]           # extra flags; -run '^$' -bench=. are added
count = 10                      # samples per benchmark
timeout = "30m"
baseline_variant = "traditional"           # the variant others are compared against

[stats]
alpha = 0.05                    # significance level
min_effect_pct = 1.0                     # smallest change worth a label
min_samples = 6                       # floor for promotion
noise_floor_note = true                    # print the explanation on generated pages

[[category]]                               # ordered; first match wins
title = "🧠 Parsing"
match = ["Parse", "Decode"]

[category_default]
title = "⚡ Basic Operations"                 # the bucket for everything unmatched

[tracked]
benchmarks = ["FindUser/result", "Concat"] # which benchmarks headline the timeline

[profile]
package = "./internal/core"                # the one package worth profiling
top = 20                               # rows kept in generated tables
kinds = ["cpu", "mem_space", "mem_objects"]

[site]
title = "myproject benchmarks"
default_theme = "light"                # light | dark | system
theme_storage_key = "myproject-theme"
extra_css = ""                     # path to your own stylesheet, copied in
highlight_langs = ["go", "bash", "toml", "json", "diff"]
loading_text = "Loading documentation... (๑•̀ㅂ•́)و✧"
not_found_text = "Looks like this page wandered off... (╥_╥)"

[[group_rule]]                             # see the naming guide
contains = "ErrorHandling"
exclude = "WithoutTry"
workload = "ErrorHandling"

[[nav]]
section = "Getting Started"
pages = [{ title = "Introduction", path = "content/home.md" }]
```

| Key                        | Default         | Notes                                                             |
|----------------------------|-----------------|-------------------------------------------------------------------|
| `project.name`             | —               | required; the only mandatory setting                              |
| `project.emoji`            | `""`            | shown in the site header; the inline SVG favicon falls back to 📊 |
| `paths.data_dir`           | `benchbook`     | relative to the config file                                       |
| `paths.site_dir`           | `docs`          | this is what you publish on Pages                                 |
| `paths.raw_dir`            | `benchbook/raw` | inside `data_dir` by default                                      |
| `bench.packages`           | `["./..."]`     | passed straight to `go test`                                      |
| `bench.args`               | `["-benchmem"]` | `benchbook` always adds `-run '^$' -bench=. -count=N`             |
| `bench.count`              | `10`            | `--count` overrides it, `--quick` sets 1                          |
| `bench.timeout`            | `30m`           | a benchmark suite can legitimately be slow                        |
| `stats.alpha`              | `0.05`          | must be > 0 and < 1                                               |
| `stats.min_effect_pct`     | `1.0`           | must be > 0                                                       |
| `stats.min_samples`        | `6`             | must be > 0                                                       |
| `site.default_theme`       | `light`         | `light`, `dark` or `system`                                       |
| `site.performance_section` | `Performance`   | nav section that generated pages go into                          |
| `site.milestone_limit`     | `500`           | hard cap on milestone pages per build                             |
| `profile.top`              | `20`            | rows in the generated `pprof -top` tables                         |

## Naming guide: workloads and variants

Benchmark names are the only taxonomy `benchbook` has, so the tool reads them deliberately. A name is split into a
**workload** and a **variant**:

```
BenchmarkFindUser/result          →  workload "FindUser"      variant "result"
BenchmarkErrorHandlingCPUWithTry  →  workload "ErrorHandlingCPU"  variant "WithTry"
BenchmarkConcat                   →  workload "Concat"          variant "traditional"
```

- The **workload** is the thing you are measuring; the **variant** is how you measure it. Two variants of a workload are
  alternatives, and the comparison against
  `bench.baseline_variant` (default `traditional`) is what makes "did the new approach win?" a one-line answer.
- The variant of a flat CamelCase name is the part that follows the workload, kept in its original spelling:
  `…CPUWithTry` gives the variant `WithTry`, not `withtry`.
- A sub-benchmark (`BenchmarkParse/case_3`) groups under its parent (`Parse`), so a table with ten cases stays readable.
- Names that do not fit the convention still work — the whole name becomes the workload.

When a package uses names that do not follow the convention, `[[group_rule]]` fixes it without renaming a single
benchmark. Rules are matched on **word boundaries** (so
`WithTry` does not match `WithoutTry`, and `DB` does not match `DBless`), which is the one detail a `strings.Contains`
implementation always gets wrong:

```toml
[[group_rule]]
contains = "ErrorHandling"      # must appear, as whole words
exclude = "WithoutTry"         # disqualifies an otherwise-matching name
workload = "ErrorHandling"      # what the report calls it after that
```

Rules are evaluated in order, first match wins.

## The generated site

`benchbook build` writes a complete static site into `site_dir` — no npm, no bundler, no server requirement:

```
docs/
  index.html                    # the shell (embedded in the binary)
  manifest.json                 # nav + project identity + thresholds for the browser
  assets/benchbook/             # css, app.js, compare.js, vendored marked + highlight.js
  content/
    benchmarks.md               # generated: every benchmark, category by category
    profiling.md                # generated: pprof -top tables, verbatim
    timeline.md                 # generated: milestone chain + inline SVG charts
    compare.md                  # generated: interactive run-vs-run page
    milestones/m001-....md      # generated: one page per milestone, immutable
    home.md                     # yours: authored pages are never rewritten
  data/
    index.json                  # exported comparison data
    current.json, m001.json …   # one document per run, copied verbatim
```

- **Timeline charts are inline SVG**, generated deterministically in Go: no chart library, no canvas, no JavaScript
  needed to see history. A hardware change is drawn as a vertical break, and the unpromoted working run appears as a
  dotted point.
- **The compare page does statistics in the browser**, from the same `data/*.json`
  documents the CLI uses, using thresholds taken from `manifest.json`.
- **Generated Markdown is fenced and labelled**; authored files under `content/` are yours and the tool will not touch
  them (it warns in the nav if one is missing).
- Deploying to GitHub Pages is: commit `docs/`, set the Pages source to that folder.

## Continuous integration

`benchmark` results from CI are noise: shared runners are throttled, neighbours are noisy and a container's CPU model
changes between providers. So the workflow
`benchbook` ships with (`.github/workflows/ci.yml`) verifies the *tool* and never runs
`go test -bench`:

```yaml
name: ci
on: [ push, pull_request ]
jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ ubuntu-latest, macos-latest, windows-latest ]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: stable
      - run: go build ./...
      - run: go vet ./...
      - run: go test -race ./...
```

What this does *not* do: run benchmarks, promote milestones, or commit anything. If you want numbers from CI for a trend
line, capture them there with `--from-file` into a job artifact and ingest them on a machine you trust — the docs site
is built from data, not from CI's mood.

## Offline and vendored assets

The site shell is vanilla HTML/CSS/JS with no build step. `marked` (`15.0.7`) and
`highlight.js` (`11.11.1`, common bundle + the Go grammar + two themes) are vendored into `internal/site/shell/vendor/`,
embedded in the binary, and pinned by SHA-256 in
[`internal/site/shell/VENDOR.md`](internal/site/shell/VENDOR.md). Nothing is loaded from a CDN at runtime, so the
generated site works on an air-gapped machine and cannot be broken by someone else's outage.

Refresh them only through the script, which refuses a checksum mismatch:

```console
$ scripts/vendor.sh            # download, verify, install
$ scripts/vendor.sh --verify   # verify what is already installed, no network
```

## Repository layout

```
cmd/benchbook/            main: wires os.Args into internal/cli
internal/cli/             the subcommands; orchestration only
internal/config/          benchbook.toml: defaults, validation, strict decoding
internal/model/           the data model
internal/model/canon/     deterministic JSON (stable key order, fixed indentation)
internal/parse/gotest/    `go test -bench` text → benchmarks, samples, variants
internal/parse/pprof/     `go tool pprof -top` tables → profile rows
internal/collect/         provenance: git, hardware (behind interfaces)
internal/runner/          process execution + the scripted Fake used by tests
internal/store/           atomic reads/writes of current.json and history/
internal/stats/           medians, Mann-Whitney U, exact distribution
internal/compare/         classification of a run pair (the one place a % is born)
internal/render/          Markdown pages, tables, escaping, inline SVG charts
internal/site/            embedded shell, manifest, data export, file writer
internal/site/shell/      index.html, style.css, app.js, compare.js, vendor/
```

Data flow, one way only: `runner` → `parse` → `model` → `store` (source of truth) →
`compare`/`stats` → `render` → `site`. Renderers and comparers are pure functions — data in, string out — which is why
the golden tests are cheap and the determinism guarantee is testable at all.

## Development

```console
$ just test          # go test ./...
$ just race          # go test -race ./...
$ just vet           # go vet ./... + gofmt check
$ just bench-check   # the CLI integration suite in internal/cli (no real toolchain)
$ just vendor        # re-verify the vendored front-end assets
$ just demo          # build the binary into ./bin
```

The test suite never runs a real benchmark: `internal/runner.Fake` answers every
`git` and `go` command, so the integration tests in `internal/cli` drive the entire tool — `init`, `run`, `milestone`,
`compare`, `summary`, `build`, `serve` — inside a temporary directory, deterministically, in under a second. Statistical
behaviour is pinned by golden vectors shared with the browser implementation, and rendering by golden files refreshed
with `UPDATE_GOLDEN=1 go test ./internal/render/`.

Every non-obvious decision, and the reason for it, is recorded in
[`DECISIONS.md`](DECISIONS.md).

## FAQ

**Where do the profiles go?**
Onto the run: `benchbook profile` attaches the `pprof -top` tables to the *current* run, and promoting copies them into
the milestone. So the order is `run` → `profile` →
`milestone`. A new `benchbook run` replaces the working run, profiles included — that is the same rule as the numbers,
because a profile of yesterday's binary is not a profile of today's.

**Why can't I promote my run?**
Almost always one of three rules, and the message names the fix: the working tree is dirty (`--allow-dirty` if you
really mean a snapshot of a half-finished state), git cannot identify the commit (`--allow-dirty` records a milestone
with no commit at all), or the samples are below `stats.min_samples` (`--force`, and the milestone is stamped ⚠ for it).

**`status` says "not directly comparable". What happened?**
The two runs have different hardware fingerprints or Go versions. `benchbook` will not subtract a number measured on an
M2 Pro from one measured on a Ryzen and call it progress. Re-measure the baseline on the machine you are on, or pass
`--force-incomparable` and read it as a rough indication, not a result.

**My benchmark is missing from the report.**
Check `bench.packages` and the filter: `benchbook run --filter FindUser --no-build`
narrows it, and the JSON holds every benchmark that `go test` actually printed. A benchmark that `go test` skipped
(wrong build tags, `-run` mismatch) is not in the capture and cannot be in the report.

**Two runs of the same code give different numbers. What is the noise floor?**
On a laptop, ±2–5% between runs is normal, which is exactly why single-sample comparisons are refused and why the test
is rank-based with a minimum effect. Close the browser, plug in the power adapter, keep the machine on a hard surface,
and take at least 6 samples. `stats.noise_floor_note` prints this reminder on the pages.

**Can I delete `docs/` and rebuild?**
Yes. `docs/` is derived; `benchbook build` regenerates it byte-identically from
`benchbook/`. The one thing you must not do is edit a generated page: it starts with
`<!-- generated by benchbook: DO NOT EDIT -->` and the next build replaces it. Your own pages live in `docs/content/`
and are never overwritten.

**I handed the JSON to a colleague; can they read it?**
Yes — that is why it is the source of truth. Every file carries `schema_version`; a newer file is refused with a message
telling you to upgrade `benchbook`, rather than being silently half-read.

**Does it work without `git`?**
Yes, with one caveat: milestones recorded outside a repository have no commit to point at, so they need `--allow-dirty`
and say so in their badge.

**Can I change where things are written?**
`paths.data_dir`, `paths.site_dir` and `paths.raw_dir` in `benchbook.toml`. Everything is relative to the config file,
so benchbook can be run from any subdirectory.

## Non-goals

`benchbook` deliberately does **not**: run benchmarks in CI, promote anything automatically, guess intent or attribute a
change to a commit, replace `pprof` with its own profiler, host a server, render arbitrary HTML from user input, or wrap
the Go toolchain in a new build system. It runs your existing `go test`, reads the output, keeps an honest history and
documents it. Everything else is your call.
